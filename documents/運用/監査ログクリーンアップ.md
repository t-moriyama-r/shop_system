# 期限切れ監査ログのクリーンアップ

`audit_logs` テーブルはシステム操作（ログイン成否・アカウント操作等）の証跡を記録し続けるため、放置するとテーブルが肥大化する。保持期間（1ヶ月）を超過したレコードを日次バッチで物理削除する（BP-006 / BP-012、NFR-009）。

改ざん防止のため `audit_logs` へは INSERT のみを許可し、UPDATE・DELETE は不可とする方針だが、**保持期間超過レコードの削除はこのクリーンアップバッチのみ例外的に許可する**。

### 改ざん防止の実装方針

アプリケーションコード上は `recordAuditLog`（INSERT）と `deleteExpiredAuditLogs`（カットオフ以前のDELETE）以外に `audit_logs` を書き換える手段を提供しないが、それに加えて DB 層でも UPDATE・DELETE を拒否するトリガー（`audit_logs_prevent_tamper`、マイグレーション `DB/migrations/0002_audit_logs_tamper_protection.sql`）を設定している。

- UPDATE は常に拒否する。
- DELETE は、トランザクションローカル設定 `app.audit_log_delete_allowed` が `'on'` の場合のみ許可する。`deleteExpiredAuditLogs` はこの設定を `SET LOCAL` で有効化した上で削除を行うため、クリーンアップバッチからの削除のみが通過する。

DBユーザー権限の分離（ロールごとにGRANT/REVOKEする方式）はDB接続構成の変更（複数ロールの発行・接続文字列の使い分け）が必要でコストが大きいため見送り、同等の効果をトリガーで実現している。

## コマンド

```sh
pnpm db:cleanup-audit-logs
```

実行時刻から 1 ヶ月前（`AUDIT_LOG_RETENTION_MONTHS = 1`）をカットオフとし、`created_at < cutoff` の監査ログを削除して削除件数を標準出力に表示する（`DB/cleanup-audit-logs.ts` → `deleteExpiredAuditLogs(auditLogRetentionCutoff())`）。

保持期間を変更する場合は `DB/audit-logs.ts` の `AUDIT_LOG_RETENTION_MONTHS` を修正する。

## 定期実行

本番運用では cron 等で日次実行する（例: 毎日深夜 3:00）。

```sh
0 3 * * * cd /path/to/shop_system && pnpm db:cleanup-audit-logs >> /var/log/shop_system/audit-log-cleanup.log 2>&1
```
