# メール送信失敗レコードの再送バッチ

顧客アカウント発行完了通知等のメール送信は非同期（fire-and-forget）で行われ、結果は `email_notification_logs.send_status` に `SUCCESS` / `FAILURE` として記録される（BP-005/BP-011）。一時的な送信エラー（SESの障害等）で `FAILURE` のまま放置されるレコードを、定期バッチで自動的に再送する。

## 対象の抽出条件

- `send_status = 'FAILURE'`
- `retry_count < 5`（`EMAIL_NOTIFICATION_MAX_RETRY_COUNT`, `DB/shop-accounts.ts`）
- 対象ショップアカウントが論理削除されていない
- 直前の更新（`updated_at`）からバックオフ時間以上経過している

上記は `findEmailNotificationRetryCandidates`（`DB/shop-accounts.ts`）で抽出する。

## バックオフ

再試行回数（`retry_count`）に応じて、5分を基準に倍化する指数バックオフとし、24時間を上限とする（`emailNotificationRetryBackoffMs`）。

| retry_count | 次回再送までの待機時間 |
| --- | --- |
| 0 | 5分 |
| 1 | 10分 |
| 2 | 20分 |
| 3 | 40分 |
| 4 | 80分 |
| 5以上 | 対象外（上限到達） |

## 再送処理の流れ

一時パスワードは平文を保持しない設計のため、手動再送信 API（項目11）と同様に、再送のたびに新しい一時パスワードを発行し直す（`Backend/lib/email/retryBatch.ts` の `retryFailedEmailNotifications`）。

1. 再送対象ごとに新しい一時パスワードを発行し、ハッシュ化する
2. `shop_accounts.initial_password_hash` を更新し、対象の `email_notification_logs` を `PENDING` に戻す（`markEmailNotificationForRetry`。`retry_count` は据え置き）
3. 通知メールを送信する（`sendShopAccountIssuedNotification`）。結果は `recordEmailNotificationResult` が同じログに反映し、失敗時は `retry_count` をインクリメントする
4. 監査ログ（`audit_logs`、`operator_type = 'system'`, `action_type = 'SHOP_ACCOUNT_NOTIFICATION_RETRY'`）に再送実行を記録する

## コマンド

```sh
pnpm backend:retry-failed-notifications
```

対象件数を標準出力に表示する（`Backend/retry-failed-notifications.ts`）。

## 定期実行

本番運用では cron 等で数分〜十数分間隔で実行する想定（例: 10分ごと）。バックオフにより、実行間隔より再送対象の待機時間が短くても同じレコードが繰り返し再送されることはない。

```sh
*/10 * * * * cd /path/to/shop_system && pnpm backend:retry-failed-notifications >> /var/log/shop_system/email-retry.log 2>&1
```

再試行上限（`EMAIL_NOTIFICATION_MAX_RETRY_COUNT`）に達したレコードは自動再送の対象外となる。恒久的な送信失敗（宛先不正等）は、SE管理画面から手動再送信 API（項目11）で個別に対応する。
